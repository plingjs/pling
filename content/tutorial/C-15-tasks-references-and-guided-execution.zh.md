# 任务、引用与引导式执行

一个空白聊天框，要求用户先学会怎么提问；而应用本身还没有告诉用户它能做什么。对预约台、管理后台或客服队列来说，这不是好的起点。用户通常知道自己要完成什么，但不知道提示词、动作 id，也不知道客户记录背后的数据库主键。

引导任务把“结果”变成**目标 + 约束 + 工作记忆**：应用给出任务名称、完成条件与边界，只询问此刻仍缺失或必须由人决定的内容，解析学员、课程等引用，最后说明发生了什么。确定性的业务写入仍可使用有序步骤，但对话不是逐字段脚本；助手要结合同一份任务状态处理问题、修正、委托选择和异常。

## 为什么任务层要独立于 Agent 循环

Agent 循环根据上下文决定下一步。日常业务任务不应该每次重新发明，但也不应该退化成“下一个字段”。应用声明目标、约束、成功判据和真正需要人决定的字段；模型把这份状态当作工作记忆，再决定这一轮该回答、追问、更新一个值、暂停，还是先不动任务。

任务层还提供了聊天记录无法替代的东西：稳定的入口列表。新员工不需要先学会提示词，就能看到“查学员会员卡”或“排一节课”。

但“有任务”不等于“任务一直出现”。真实页面里，任务是否可用取决于路由、弹窗、选中行和用户权限。把这些判断塞进每个组件，很快会出现两套事实：页面一套，助手一套。任务目录（task catalog）负责把这层判断集中起来。

### 任务目录负责“此刻能做什么”

页面用 `pling.task.define()` 注册一个任务，并声明它的上下文：

```ts
pling.task.define({
  definition: courseTask,
  guide: courseGuide,
  controller,
  route: "/courses",
  scope: "create-course-form",
  autoStart: true,
  onCommand,
});
```

- `route`：只在当前路由匹配时可用；
- `scope`：只有某个区域或弹窗存在时可用；
- `autoStart`：上下文匹配时自动展示引导；
- 省略二者表示全局任务，但仍要由页面或助手显式开启。

任务目录只保存注册信息和当前 active guide，不执行任务。真正的写入仍然交给 `controller`，再由现有执行器处理。

### 助手可以从清单中选择，但不能发明任务

模型每轮会拿到当前可用任务、字段和步骤摘要。用户说“帮我新建一门瑜伽课”时，模型可以调用一个窄动作 `pling_start_task`：

```json
{
  "task": "course.create",
  "values": { "name": "瑜伽基础", "teacherId": "teacher_zhoumin" }
}
```

这条动作只接受当前可用的任务 id；`values` 也只能包含该任务声明过的字段。未知 id 或未知字段直接返回 `INVALID_ARGS`。传入值只是预填一次任务运行，不会跳过动作自己的权限、确认和审计。

因此，现在支持的是“助手从已注册任务中创建一次运行”。任务激活后，模型还可以通过独立的 `pling_update_task` 动作更新这次运行的工作记忆。它只能写当前任务、声明过且允许 Agent 写入的字段，不会直接执行业务写入；页面可以订阅运行快照，把变化同步回原表单。以后若要让助手组合出新的流程，也必须先把任务模板注册进来，经过校验和用户确认，再进入同一个目录；不能让模型直接拼动作序列。

三条边界需要同时成立：

| 层 | 负责 | 不能负责 |
| --- | --- | --- |
| 应用任务定义 | 目标、约束、成功判据、字段、查找来源、确定性步骤 | DOM 选择器或模型传输 |
| 任务运行 | 已填字段、进度、错误、取消 | 第二套权限系统 |
| 现有动作执行器 | 可用性、确认、执行、验证 | 业务任务命名 |
| Agent 循环 | 模糊请求与异常处理 | 成为日常任务的唯一入口 |

## 只描述人需要决定的内容

任务字段不是数据库列。它存在，是因为用户必须做选择。当前店铺、操作人、请求时间与授权范围来自会话和服务端；客户标识来自选中的行、搜索结果，或由服务端解析的稳定引用。

下面的定义只询问学员与会员卡，不询问 `shopId`、`operatorId`，也不要求用户填写学员主键。

```ts
import { createTaskController } from "@plingjs/agent";

const tasks = createTaskController({
  invoke: (action, args) => businessApi.invoke(action, args),
});

tasks.register({
  id: "student.cards",
  title: "查看学员会员卡",
  description: "按姓名或手机号找到学员，再读取会员卡。",
  objective: "找到正确学员，并展示他真正可用的会员卡。",
  constraints: ["重名时必须让用户明确选择。"],
  successCriteria: ["返回的卡片属于用户确认的那名学员。"],
  fields: [
    {
      name: "studentRef",
      label: "学员",
      type: "lookup",
      recommended: "student_li_na",
      lookup: (query) => businessApi.searchStudents(query),
    },
  ],
  steps: [
    { label: "读取学员", action: "get_student" },
    { label: "读取会员卡", action: "get_student_cards" },
  ],
});
```

动作名仍然属于现有注册表或业务服务。任务控制器只把参数交给宿主提供的 `invoke`，不自己操作 DOM、不替动作审批，也不重新解释权限。

### 先接住用户已经说出的内容

引导任务不等于逐字段问答。用户说“孕妇瑜伽，陈老师，2 星，介绍自动填写”时，页面应该一次写入已经明确的值，然后只追问缺失、冲突或必须由人完成的部分。逐项弹问会让助手像一张会聊天的表单，反而比直接填写更慢。用户说“卡片你来选”时，模型可以使用该字段声明的 `recommended` 值，即使其他必填字段还没填；推荐值只是建议，不是自动写入。

字段值不需要页面先做一轮意图分类。模型拿到 active task 的字段、当前值与缺口后，直接调用 `pling_update_task` 写入它从整句话里理解到的值；页面只负责校验这些值是否属于声明过的字段、类型是否匹配、业务约束是否满足。校验失败时不写入任何部分值，模型可以重试或向用户追问。后续的“难度改成 4 星”同样是当前任务的修正，而不是一次全新的创建请求；是否理解正确由模型结合工作记忆判断，页面不再维护一套正则或关键词表。

## 先把引用解析成人能确认的结果

人认名字、行和最近活动，API 要稳定引用。引导任务要跨过这道边界，同时不让人或模型去猜。

| 来源 | 例子 | 界面做法 |
| --- | --- | --- |
| 当前选择 | 学员详情页中的一行 | 绑定行上下文，不再询问 id |
| 小型封闭集合 | 课程类型、会员卡模板 | 带标签值的下拉框 |
| 大集合 | 学员、课程 | 由 `lookup` 调搜索接口 |
| 服务端事实 | 店铺、操作人、请求时间 | 服务端推导，不作为字段 |

查找结果必须带足以区分重名的信息。两个“李娜”需要不同的手机号尾号、会员编号或最近上课时间。写操作不能默认选第一条。

引用也会过期。页面刷新前的引用可能失效，一个店铺得到的引用不能被另一个店铺接受。执行写操作前，服务端要重新解析引用，并校验权限、归属与有效期。浏览器里的选择只是意图，不是授权。

## 绑定已选记录，不再重复索要 id

最可靠的引用，是页面已经拿到的那一个。员工打开某节课的行，点“写备注”时，课程 id 不是表单要问的问题，而是当前视图的事实。通过 `start(id, values, binding)` 传入，可以把它挡在用户输入和模型提示词之外。

任务离开这条记录就无法工作时，用 `requiresRecord: true` 声明。通用任务列表仍可以显示入口，但必须从表格行或详情页带着记录打开，而不是启动一个空运行。步骤里用 `args(values, binding)` 读取 `binding.record?.id`；表单只问备注。对模型也更安全：它不必猜，也不该复述一个不透明的 id。

## 保持一条执行路径

任务步骤引用已注册的动作。动作可以由按钮、函数级工具、业务 API 或受治理的 Surface 调用实现。应用可以先接可见流程，稳定后再把某一步换成只读 API，而任务名称和用户心智不变。

查询通常更适合只读 API：更快，也不必为了回答一个问题滚动整张表。写入通常更适合走应用服务层，这样原有校验、幂等、审计和通知仍然生效。裁剪图片、输入验证码、拖动排期等视觉操作继续走 UI。

原则不是“API 优先”或“DOM 优先”，而是任务必须经过和真人操作相同的业务边界。成功不是 HTTP 200；写入后要能通过刷新、回读或已声明的期望观察到结果。

## 让进度可读

任务界面要回答四个问题，但不泄露实现细节：

1. 用户要完成什么？
2. 应用现在需要用户提供什么？
3. 正在执行哪一步，为什么？
4. 改了什么，或者为什么停下？

步骤文案要写给人看：“检查时间段冲突”“创建课程”“核对会员卡余额”。原始动作 id、参数对象和堆栈留在诊断面板。错误也一样：先说明原因和下一步安全做法，内部错误码供支持人员查。

进度里有三个时刻，很容易被误合并。`planned` 表示路线已经确定，但还没有执行；`running` 表示调用正在进行；`verifying` 表示调用已返回，页面正在被读取以核对结果。只显示“运行中”的界面，无法告诉用户写入到底发生了没有。

任务级确认也不同于动作审批。任务问的是“这份计划要不要继续”，执行器仍然判断“这次写入是否允许”。两者谁也不能覆盖谁。`waitingFor: "confirmation"` 的快照由 `confirm()` 推进；`waitingFor: "handoff"` 则在等人于页面上完成操作。

## 为人工作与歧义暂停

有些步骤必须由人完成：签名、验证码、支付确认，或无法可靠描述的视觉选择。任务应暂停并交还控制权，而不是模拟点击。人完成后，从下一步继续，不从头重跑。

这类步骤用 `handoff` 标记。运行进入 `waitingFor: "handoff"`，由宿主负责观察页面并判定操作完成。长执行桥也可以用 `context.report("waiting", "handoff")` 或 `report("verifying")` 上报同样的子状态，避免界面只会转圈。

歧义不同于人工步骤。两个学员同名时，问清楚是哪一个；课程时间不可用时，说明冲突并给出其他时间。不要静默换一条记录，也不要留下半成品。任务运行应停在可见、可恢复的状态。

## 失败也是契约的一部分

一次运行从收集字段进入就绪，然后经过执行到完成、失败或取消。缺少必填字段时不能执行；写入失败时停止；补充信息失败时可以跳过，但必须让人看见；取消会中止正在进行的步骤，不能报告成功。

| 状态 | 对用户的意思 | 恢复方式 |
| --- | --- | --- |
| `collecting` | 还需要信息 | 补全指定字段 |
| `ready` | 可以开始 | 运行或切换任务 |
| `running` | 正在执行某一步 | 等待或取消 |
| `done` | 步骤已完成 | 查看结果 |
| `failed` | 某一步失败 | 阅读原因，重试或改输入 |
| `cancelled` | 用户停止了任务 | 准备好后重新开始 |

## 实现放在哪里

业务任务定义留在应用。与框架无关的运行模型在 `@plingjs/agent`。现有动作注册表与执行器仍在 `@plingjs/core`。任务渲染属于适配层，不属于 Agent 循环。这样 Vue、React、Vue 2 与原生 JS 可以共用同一套任务模型，而不出现四套执行引擎。

任务目录在 `@plingjs/agent`，它只判断可用性、激活和命令转发。适配器负责把 active guide 放进自己的界面。Vue 3 的 `<AgentInline>` 会自动订阅任务目录并渲染引导；业务页面不需要再手写一套聊天壳，也不必手动挂载任务卡。只有产品确实需要另一种呈现时，才使用 `#task` 插槽替换默认引导。

`@plingjs/vanilla` 仍然保留 `createTaskPanel()` / `createTaskCard()` 这类底层渲染能力，供原生 JS 或自定义布局使用。它们和内置助手共用同一份任务运行、查找、确认与失败处理，不形成第二套执行引擎。

下一步动作的紧凑行由 `@plingjs/dom` 提供，而不是每个适配器各写一份。`GuideActionItem` 把动作压到一行：短标签、业务命令、可选类型；长推荐放在 `preview`，单行省略，完整值仍在聊天正文、`title` 与 `aria-label`。这样按钮宽度不会由业务文案决定，操作行也不会把对话挤走。渲染器只发出命令，写字段、定位和调用执行器仍由宿主完成。

`registerTaskLookupActions` 还可以把 lookup 字段注册成只读搜索动作。模型先按人名搜索，再带着与用户看到的同一批候选去写入。这样，“模型知道这里需要 id”与“人知道自己指的是哪一行”之间不再断档。

同一个任务也可以通过 Surface 的 `tasks` 描述给外部 Agent。描述是地图，不是钥匙：它解释哪些能力配合完成一件事，但 `invoke` 仍要经过现有暴露清单、会话作用域、审批与审计。

## 可运行示例

[课程管理后台](/demos/course-workspace/?lang=zh)把这一章的几件事放在同一页：新建课程、重名查找、新增老师、时段冲突失败、绑定课程行的备注任务，以及任务卡执行后同步更新的课程库和课表。先跑五个任务，再看[源码与接入说明](/zh/examples/course-workspace)。

课程创建演示采用更接近真实后台的方式：进入页面时打开原有的“创建新课程”表单，助手在聊天里承接任务。用户可以直接输入一整段课程描述，模型把它理解为若干字段并调用 `pling_update_task`，页面校验后一次写回原表单，只追问仍然缺失的内容；有问题的老师、难度或需要本人上传的封面会定位到原字段。这个案例故意用 `task-placement="none"` 隐藏了内置任务卡和字段轨道：课程表单本身已经连续，聊天上方再放一条并行的步骤条只会多一条操作路径。字段缺口、建议、定位和核对操作放在对话末尾的操作行里，信息齐了以后给出只读摘要和“确认保存”，写入后从课程库回读结果。`examples/shared/course-create/guide.ts` 负责引导文案、字段状态与页面命令，`CourseWorkspace.vue` 里的原表单仍是业务输入的唯一来源；`legacy-intake.ts` 只是早期确定性解析的历史快照，当前 demo 不再引用它。

## 核对清单

- 用户不写提示词也能开始任务；任务只在路由和作用域匹配时出现。
- 每个字段都对应一个人能做出的决定。
- 查找出现重名时，必须明确选择。
- 服务端重新校验引用及其店铺、会话范围。
- 行级任务通过绑定拿到记录，不靠隐藏输入框。
- 每个步骤都调用现有动作或业务服务；助手只能选择已注册任务，不能编造 id 或字段。
- 界面能区分成功、失败、取消与可选步骤跳过。
- `planned`、`running` 与 `verifying` 没有被合成一个标签。
- 写入后经过验证，而不是从请求成功推断。
- 原始动作 id 与参数只出现在诊断中。
