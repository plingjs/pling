# 任务、引用与引导式执行

一个空白聊天框要求用户先学会怎么提问。应用本身还没有告诉用户它能做什么。对预约台、管理后台或客服队列来说，这不是好的起点。

用户通常知道自己要完成什么，但不知道提示词、动作 id，也不知道客户记录背后的数据库主键。引导任务把“结果”变成**目标 + 约束 + 工作记忆**：应用说明要达成什么、哪些边界不能越过、怎样算完成，助手再结合当前页面决定这一轮该回答、追问、执行，还是停下来等人。

## 先判断是否需要任务层

一张短表单通常不需要任务层。页面用 `v-scope`、`v-record` 和 `v-tool` 声明区域、草稿和动作，助手就能理解一句话、操作真实控件并核对结果。这样接入最少，也最接近原有业务代码。

任务层解决另一类问题：

- 流程跨多个页面，需要保留进度；
- 弹窗关闭或路由切换后，任务还要继续；
- 任务要从固定入口反复启动；
- 多个步骤必须共用一份工作记忆；
- 外部 Agent 需要一份可审计的任务说明和完成边界。

只有出现这些条件，才值得增加任务声明。

| 场景 | 推荐做法 |
| --- | --- |
| 一页内完成，字段稳定，保存路径单一 | `v-scope` + `v-record` + `v-tool` |
| 弹窗关闭后结果还要继续存在 | 加一个 `pling.task.goal()` |
| 任务跨路由、需要取消和完成记录 | `pling.task.goal()` |
| 外部 Agent 要复用同一份 playbook | `pling.task.goal()` |
| 字段需要校验、查找、固定多步执行 | 进阶 `TaskDefinition` + `TaskController` |

这张表的第一列不是“能力从低到高”。它是接入成本从低到高。能用页面动作说清楚的事，不要写进任务定义。

## 目标回答页面回答不了的问题

页面动作能说明“这个按钮做什么”“这个输入框接收什么值”。它说不清“这件事在弹窗关闭后还算不算数”。

一个目标只包含：

```ts
const disposeGoal = pling.task.goal({
  id: "course.create",
  title: "创建课程",
  goal: "在课程管理里新建一门课程，保存后回读课程库确认新课程在第一位。",
  constraints: [
    "页面上的动作是唯一操作入口，不要另造表单。",
    "封面必须由用户亲自上传。",
  ],
  successCriteria: [
    "新课程出现在课程库第一位",
    "名称、老师、可用卡和封面与用户确认的一致",
  ],
});
```

没有字段表，没有步骤数组，没有执行回调。字段从真实页面读，执行走真实动作。

目标解决四件事：

1. **连续性**：显式启动后，弹窗关闭或区域消失，目标仍然 active。
2. **可用范围**：`route` 和 `scope` 决定目标从哪里能开始。
3. **生命周期**：用户可以取消，模型可以在成功条件满足后标记完成。
4. **外部说明**：Surface 可以拿到同一份目标、约束和成功条件。

目标不解决权限。每条动作仍然经过自己的风险、确认、作用域和审计。目标也不执行保存。保存永远是页面自己的动作。

## 任务目录负责“此刻能做什么”

页面用 `pling.task.goal()` 或 `pling.task.define()` 注册任务。任务目录（task catalog）负责判断当前上下文里哪些任务可用，同一时刻只激活一个。

```ts
pling.task.goal({
  ...courseGoal,
  route: "/courses",
  scope: "course-catalogue",
});
```

- `route`：只在当前路由匹配时可用；
- `scope`：只有某个区域存在时可用；
- `keepActive`：显式启动后，短暂离开上下文是否保留；
- 省略路由和作用域表示全页面可用，但仍要由人或模型显式启动。

把可用性判断放在目录里，页面和助手就不需要各维护一套。页面负责渲染真实控件，目录负责“这个任务现在能不能开始”，执行器负责“这条动作能不能执行”。

## 助手可以从清单中选择，但不能发明任务

模型每轮会拿到当前可用的目标或任务。用户说“帮我新建一门瑜伽课”时，模型可以调用窄动作 `pling_start_task`：

```json
{
  "task": "course.create"
}
```

这条动作只接受当前可用的任务 id。未知 id 直接返回 `INVALID_ARGS`。模型不能临时拼出一个不存在的工作流，也不能绕过动作自己的权限。

目标启动后，模型还可以看到一个完成动作 `pling_complete_task`。它只在成功条件满足时调用，只关闭目标，不写业务数据。

如果任务是进阶定义，模型还可能看到 `pling_update_task`、`pling_focus_field`、`pling_review_task`、`pling_propose_save` 和 `pling_cancel_task`。这些动作由任务声明决定，不是默认全部开放。

三条边界同时成立：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 页面 | 真实控件、区域、记录、保存函数 | 意图识别、任务调度 |
| 任务目录 | 可用性、激活、取消、完成 | 业务写入、权限放宽 |
| 模型 | 理解这一句话、选择动作、说明结果 | 发明动作、绕过确认 |

## 用户已经说出的内容要先接住

创建课程需要很多项。逐项追问会把对话变成表单问答。这个示例没有在页面里写意图分类器，也没有把“下一步问什么”写死。

用户说：

```text
孕妇瑜伽，陈静，2 星，月卡，介绍自动填写
```

模型看到目标、约束、页面动作、草稿记录和缺口，把这句话理解成多个值。它调用页面动作，把名称、老师、难度、可用卡和介绍写进真实表单。随后只问真正缺的内容，例如封面。

如果老师不在列表里，它停下来问人，不会拿相近的名字替换。如果用户说“随便填”，动作说明允许在明确委托时生成介绍；如果没有委托，它不替用户编造。

字段校验属于页面。原生控件的 `min` / `max`、`select` 的选项集合、禁用和只读状态，都在写入时检查。类型不对、选项不存在或字段不存在时，动作返回原因，不会留下填了一半的表单。

## 引用要先解析成人能确认的结果

真实任务里，用户说的是“李娜的会员卡”，不是 `student_0018`。模型不应该猜主键，也不应该让用户输入主键。

进阶任务可以声明 `lookup` 字段：

```ts
const studentField: TaskField = {
  name: "studentRef",
  label: "学员",
  type: "lookup",
  minChars: 2,
  searchAction: "search_students",
  lookup: async (query, { signal }) => api.searchStudents(query, { signal }),
};
```

模型调用 `search_students`，拿到与用户看到的同一批候选，再带着用户确认的结果写入。重名时必须展示候选人和脱敏信息，不能静默选第一个。

小集合可以直接用 `values`。大列表用异步查找，避免把几千条记录塞进上下文。

## 绑定已选记录，不再重复索要 id

很多任务从表格行或详情页开始。用户点“写备注”时，页面已经知道是哪一节课、哪张订单。

`TaskBinding` 承载页面事实：

```ts
const addNote: TaskDefinition = {
  id: "lesson.note",
  title: "写课程备注",
  requiresRecord: true,
  fields: [{ name: "note", label: "备注", type: "textarea" }],
  steps: [{
    label: "保存备注",
    action: "update_lesson_note",
    args: (values, binding) => ({
      lessonId: binding.record?.id,
      note: values.note,
    }),
  }],
};
```

`requiresRecord` 为真且没有记录 id 时，`start()` 会抛错。任务列表应把这类任务显示成入口，而不是允许在没有上下文时直接启动。

## 保持一条执行路径

任务层不另造执行器。进阶任务的步骤调用已经注册的动作，经过同一个执行器、同一套确认和审计。

```ts
const controller = createTaskController({
  invoke: (action, args, context) => executor.execute(action, JSON.stringify(args), context),
});
```

目标层更简单：它根本不执行动作。模型直接调用页面动作，执行器逐条处理。

无论哪条路径，都不允许通用 `click(selector)` 或 `eval` 这类逃逸口。能做的操作必须是页面声明过的窄动作。

## 让进度可读

用户需要知道现在在做什么、还差什么、是否失败。任务快照承担这份可见状态。

| 状态 | 对用户的意思 | 恢复方式 |
| --- | --- | --- |
| `collecting` | 还需要信息 | 补全指定字段 |
| `ready` | 可以开始 | 运行或切换任务 |
| `running` | 正在执行某一步 | 等待或取消 |
| `waiting` | 等待确认或人工接力 | 确认，或在页面上完成 |
| `verifying` | 动作已返回，正在核对结果 | 查看证据后继续 |
| `done` | 已完成 | 查看结果 |
| `failed` | 某一步失败 | 阅读原因，重试或改输入 |
| `cancelled` | 用户停止了任务 | 准备好后重新开始 |

目标层只有“进行中”和“已完成”两个状态。它没有字段轨道，也没有步骤控制器。界面只显示目标、取消和完成，不显示假的表单控件。

## 人工步骤与歧义

有些步骤只能由人完成：签名、验证码、支付确认，或无法可靠描述的视觉选择。任务应暂停并交还控制权，而不是模拟点击。

在页面动作里用 `handoff` 标记：

```ts
v-tool="{
  id: 'course_cover',
  desc: '上传课程封面',
  handoff: {
    reason: '请选择一张本地图片',
    expect: { desc: '页面已记录用户选择的封面', check: () => draft.cover }
  }
}"
```

运行进入等待，由宿主观察页面并判断是否完成。模型不能替用户选择文件，也不能伪造完成状态。

歧义不同于人工步骤。两个学员同名时，问清楚是哪一个；课程时间冲突时，说明冲突并给出其他时间。不要静默替换记录，也不要留下半成品。

## 失败也是契约的一部分

缺少必填项时不能保存；写入失败时停止；可选步骤失败时可以跳过，但必须让人看见；取消会中止正在进行的步骤，不能报告成功。

动作的 `expect` 负责结果验证：

```ts
expect: {
  desc: "新课程出现在课程库第一位",
  check: () => courses.value[0]?.id === newCourseId.value,
}
```

执行器在动作返回后检查。条件不成立时，失败原因可见。完成卡展示这次回读的结果，不是预写的“成功”文案。

## 实现放在哪里

业务任务定义留在应用。与框架无关的运行模型在 `@plingjs/agent`。动作注册表与执行器在 `@plingjs/core`。任务渲染属于适配层，不属于 Agent 循环。

任务目录只判断可用性、激活和命令转发。Vue 3 的 `<AgentInline>` 自动订阅目录并渲染引导；业务页面不需要再手写聊天壳，也不必手动挂载任务卡。

Vue、React、Vue 2.7 和原生 JS 共用同一份任务模型和 DOM 渲染器，不出现四套执行引擎。

同一个目标也可以通过 Surface 的 `tasks` 描述给外部 Agent。描述是地图，不是钥匙：它解释哪些能力配合完成一件事，但 `invoke` 仍要经过现有暴露清单、会话作用域、审批与审计。

## 核对清单

- 用户不写提示词也能开始任务；目标只在路由和作用域匹配时出现。
- 启动目标不会打开弹窗、填写字段或保存。
- 每个字段都对应一个人能做出的真实操作。
- 自定义控件用真实点击或参数化动作接入，不改写成第二张表单。
- 查找出现重名时，必须明确选择。
- 行级任务通过绑定拿到记录，不靠隐藏输入框。
- 每个写入动作都经过现有执行器和回读验证。
- 界面能区分成功、失败、取消与人工等待。
- 完成目标之前，页面已经满足成功条件。
- 原始动作 id 与参数只出现在诊断中。
